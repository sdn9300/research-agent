## 1. Purpose of This Document

This defines exactly how the Research Agent's correctness, reliability, and cost-efficiency are measured — independent of how it was built. The Implementation Plan tells you what gets coded; this tells you how its output is judged, scored, and gated. No success claim elsewhere in the system's documentation is valid unless it traces back to a result produced under this plan.

---

## 2. Evaluation Philosophy

Per the project's standing engineering principle, predictive/qualitative claims are subordinated to measured, falsifiable evidence wherever ground truth is available. Unlike the Altitude & Heat Adaptation project — where ground truth is inherently limited and outputs must be ranges — the Research Agent operates against **verifiable, fully knowable ground truth** (real company facts). This means the evaluation bar here is binary and strict: a claim is either correct, incorrect, or properly flagged as low-confidence. There is no "directionally right" credit.

---

## 3. Evaluation Dimensions

| Dimension | What it measures | Why it matters |
|---|---|---|
| **Factual Accuracy** | Does the brief's content match verified ground truth? | Core utility — a wrong brief actively harms downstream tailoring/outreach quality |
| **Citation Integrity** | Does every claim trace to a real, retrievable chunk? | This is the guardrail's entire reason for existing — zero tolerance |
| **Confidence Calibration** | Does the agent correctly flag low-source-coverage cases instead of fabricating? | Distinguishes honest uncertainty from silent failure |
| **Cost Efficiency** | Tokens + tool calls consumed per run | Determines whether the system is sustainable to run repeatedly, not just once for a demo |
| **Latency** | Wall-clock time per run | Determines whether downstream agents (AlignResume, Overture) can use this interactively |
| **Regression Stability** | Does a code/prompt change degrade prior performance? | This is what makes the CI eval-gate meaningful rather than decorative |

---

## 4. Evaluation Dataset Specification

| Property | Specification |
|---|---|
| Size | 15–20 companies |
| Composition | Mix of company sizes — large/well-documented (e.g., established tech firms), mid-size, and at least 3–4 small/early-stage companies with deliberately thin web presence |
| Facts per company | 3–5 ground-truth facts (e.g., founding year, primary product, funding stage, HQ location, headcount range) |
| Sourcing rule | Every ground-truth fact must be independently verifiable from a source *the practitioner manually checked*, not generated by an LLM |
| Freeze rule | Dataset is frozen after Phase 0 (Mission Plan Gate 1) and not modified to make passing easier — modification after freeze invalidates any subsequent accuracy claim |
| Adversarial subset | A minimum of 2 test cases are deliberately constructed to tempt fabrication (e.g., a company with almost no public information) — these test the confidence-calibration dimension specifically, not factual accuracy |

---

## 5. Scoring Methodology

### 5.1 Factual Accuracy Score

```
Per-company score = (facts correctly surfaced) / (total facts for that company)
Aggregate accuracy = mean(per-company scores) across all companies
```

A fact is scored **correct** only if it (a) appears in the output and (b) matches ground truth. A fact that is **absent** is scored as incorrect, not neutral — silence is not credited as caution unless it is accompanied by an explicit confidence flag (see 5.3).

### 5.2 Citation Integrity Score

```
Citation integrity = (claims with a valid, resolvable citation) / (total claims in output)
```

Required result: **100%** on every passing run. Any claim without a valid citation is an automatic fail for that run, regardless of whether the claim happens to be factually correct — the guardrail is being tested, not the model's luck.

### 5.3 Confidence Calibration Score

For the adversarial low-source-coverage subset specifically:

```
Calibration pass = agent explicitly flags low confidence AND does not fabricate a specific, unverifiable claim in its place
```

Scored pass/fail per adversarial case, reported separately from the main accuracy number — conflating these would hide whether the guardrail is actually doing its job on the hard cases.

### 5.4 Cost and Latency

Recorded per run, not scored pass/fail, but tracked against the targets below:

| Metric | Target (from NFRs) |
|---|---|
| Latency | < 15 seconds per company |
| Tool calls | Bounded by the per-run budget set in Phase 2 (T2.3) |
| Token cost | Documented and stable — flag any run that deviates >2x from the running average for investigation |

## 6. Pass/Fail Thresholds Summary

| Metric | Threshold | Consequence if missed |
|---|---|---|
| Aggregate factual accuracy | ≥ 80% | Mission Plan §7 Remediation Sub-Phase triggered |
| Citation integrity | 100% | Build is not considered functional regardless of accuracy — non-negotiable gate |
| Confidence calibration (adversarial subset) | 100% pass | Self-check node requires rework before proceeding |
| Latency | < 15s average | Documented as a known limitation if missed; not a hard blocker unless it exceeds 30s |
| Cost | Stable within documented range | Investigated, not automatically blocking |

---

## 7. Evaluation Execution Procedure

| Step | Action |
|---|---|
| 1 | Load frozen fact-set (`eval/fact_set.json`) |
| 2 | For each company, run the full Research Agent graph exactly as it would run in production — no special "eval mode" shortcuts that bypass real tool calls |
| 3 | Log full run metadata (prompt version, chunks retrieved, latency, cost) per company |
| 4 | Score each company against §5.1–§5.3 |
| 5 | Compute aggregate scores per §6 |
| 6 | Write results to `eval/results/run_<id>.json`, timestamped and never overwritten — historical runs are kept for regression comparison |
| 7 | Compare current run against the most recent prior run; flag any metric that regressed by more than a defined tolerance (e.g., accuracy drop >5 percentage points) |

---

## 8. CI Integration (Regression Gate)

| Trigger | Action |
|---|---|
| Pull request modifying any prompt, retrieval logic, or graph node | Eval suite runs automatically against the full frozen fact-set |
| Aggregate accuracy drops below 80% | CI check fails, merge blocked |
| Citation integrity drops below 100% | CI check fails, merge blocked — treated as more severe than an accuracy dip |
| All thresholds met | CI check passes, merge permitted |

**Validation requirement (per Implementation Plan T3.4):** before trusting this gate, a deliberately degraded prompt must be pushed to a test branch and confirmed to actually fail the check. An eval gate that has never been observed to fail is not a proven gate.

---

## 9. Rubric for Manual Spot-Checks

Even with automated scoring, a subset of outputs should be manually read end-to-end, since automated fact-matching can miss subtler issues:

| Check | Pass criteria |
|---|---|
| Tone/coherence | Brief reads as a coherent narrative, not a disjointed fact-dump |
| Citation plausibility | Spot-check 2–3 citations per manual review — does the cited chunk actually say what the claim asserts, not just contain matching keywords? |
| Over-hedging | Confidence flags are used appropriately, not as a blanket disclaimer covering for genuinely retrievable information |
| Source diversity | Brief isn't built entirely from one low-quality source when better sources were available within the tool-call budget |

## 10. Reporting Format

Each evaluation run produces a report with this structure, for direct reuse in documentation/resume claims:

```
Run ID: run_004
Date: <timestamp>
Prompt version: v1.3
Companies evaluated: 18
Aggregate factual accuracy: 83.3%
Citation integrity: 100%
Confidence calibration (adversarial subset, n=3): 3/3 passed
Average latency: 11.2s
Average cost per run: $0.0038
Regression vs. run_003: +2.1 percentage points accuracy, no change in citation integrity
```

This exact structure is what gets quoted in the README, the resume bullet, and the interview walkthrough — a single source of truth for every downstream claim about the system's performance.

---

## 11. What This Plan Deliberately Does Not Cover

- **Multi-company batch performance** — out of scope per the Problem Statement; evaluation here is single-company correctness only
- **User-perceived quality surveys** — no human-in-the-loop subjective rating system is built at this stage; correctness is judged against hard ground truth only
- **Live A/B testing in production** — not applicable; there is no production traffic yet, only the frozen eval set
