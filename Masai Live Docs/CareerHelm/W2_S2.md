## The one idea this class is built on

> **Aggregate analysis is a different question from per-item analysis â€” and it's where the
> value is.**

Every job board ever built shows you **one listing at a time**. A single listing answers *am I
a fit for this?* Two hundred listings together answer something else entirely: *what is the
market paying for, and where am I short?*

A human cannot answer the second question. Not because it's hard â€” because of arithmetic. To
know that 180 listings want Kubernetes you must read 180 listings, remember them all, and
count. Your loop did that last night.

And here's the part worth sitting with: **the most valuable output of this project is the
cheapest code in it.** It's a `GROUP BY`. There's no AI in the core of it at all.

Three weeks of fetching, dedup, extraction, normalisation and scoring weren't the insight. They
were building a table where the obvious question became askable. That's what engineering usually
is â€” the plumbing is what makes the valuable question cheap.

This is also why "just ask a model what skill to learn" doesn't work. The model has no idea
what's in *your* market; it'll give you the same confident, generic answer it gives everyone.
**The answer isn't in the model. It's in your data.**

## PROMPT C4-P2 â€” Canonicalisation

**What it does:** The boring prerequisite. Right now your database contains `k8s`,
`kubernetes`, `Kubernetes` and `Kubernetes (EKS)` as four separate skills, because your
extractor read job descriptions written by 200 different people. Skip this and your real top gap
gets split into fragments and pushed down the ranking.

```text
Build skill canonicalisation. Deterministic only â€” no LLM in this file.

1. edgedash/skills.py
   - `canonical(raw: str, aliases: dict) -> str`
     Lowercase, strip whitespace and surrounding punctuation, drop
     parenthetical qualifiers ("kubernetes (eks)" -> "kubernetes"), collapse
     internal whitespace, then apply the alias map.
   - Pure function. Same input, same output. No network, no model.

2. Add a `skill_aliases` map to config.yaml, pre-seeded with the common
   collisions for a data/software role. At minimum:
     k8s -> kubernetes
     js / node / nodejs / node.js -> javascript is WRONG â€” keep node
       separate from javascript, they are different skills
     postgres / postgresql / psql -> postgres
     gcp / google cloud / google cloud platform -> gcp
     ml / machine learning -> machine learning
     ci/cd, ci cd, cicd -> ci/cd
   Add a comment at the top of the map saying this is MINE to edit and
   that adding entries is expected as I see my own data.

3. `python -m edgedash.skills --audit`
   Read every extracted required_skills value in the database and print:
   - the 40 most common raw skill strings with their counts
   - which canonical form each maps to
   - a clearly separated list of raw strings that are ONLY seen once,
     since those are usually typos, junk, or full sentences the extractor
     mistakenly captured as a skill
   Read-only. This is how I find aliases I'm missing.

4. Tests for canonical(): case, whitespace, parentheses, an aliased term,
   a term with no alias, and empty string.

Show me canonical() first, then the alias map.
```

**Then run the audit â€” this is real data about your own market and it's genuinely interesting:**

```bash
python -m edgedash.skills --audit
```

**Check before moving on:** you can see your own duplicates in the top 40, and you add at least
three aliases yourself. That's part of the assignment.

**The trap: over-merging is worse than under-merging.** Note the prompt explicitly refuses to
merge Node into JavaScript. They're different skills in a hiring context, and merging them gives
you a top gap so broad it's useless â€” *"you're missing JavaScript,"* what do you do with that?

- **Under-merging is visible.** You see `k8s` and `kubernetes` next to each other and fix it in
  30 seconds.
- **Over-merging is invisible.** Your report looks clean and tells you the wrong thing.

**When unsure, leave them separate.** Fragmentation you can see beats tidiness you can't check.
That's a general data-cleaning rule, not a quirk of this project.

**The singletons list** at the bottom of the audit is your extractor's junk drawer â€” that's where
you find that it once decided "must be a self-starter" is a required skill.

## PROMPT C4-P3 â€” The Gap Analyzer

**What it does:** The most valuable output of the project. Note how short it is, and note that
there's no model call in it anywhere.

```text
Build the Gap Analyzer. Deterministic â€” no LLM call anywhere in this file.

edgedash/agents/gap_analyzer.py â€” a `GapAnalyzer` implementing the
existing Agent protocol.

1. Read every scored listing with extracted facts from storage.
   Skip listings with no score â€” they haven't been analysed yet.

2. For each listing, for each required_skill NOT in config.skills
   (compared canonically, via edgedash.skills.canonical):
   that's a gap attributable to that listing.

3. For each canonical missing skill, compute:
   - listings_blocked: how many listings require it and I don't have it
   - opportunity_cost:  sum of (listing.score / 100) for those listings
                        â€” this is the ranking key, per rule 24
   - mean_score:        mean fit score of those listings
   - top_score:         highest-scoring listing blocked by this gap
   - example_ids:       up to 5 listing IDs, highest score first (rule 26)
   - also_nice_to_have: count where it appeared as nice_to_have, tracked
                        SEPARATELY and never mixed into the required count

4. Rank by opportunity_cost descending. Report the top 10.

5. Per rule 27, alongside every skill report the sample size, and flag any
   gap computed from fewer than 3 listings as "low confidence".

6. Per rule 25, write a TIMESTAMPED SNAPSHOT to a skill_gaps table via the
   storage module â€” run_id, computed_at, skill, listings_blocked,
   opportunity_cost, mean_score, example_ids. Never overwrite a previous
   run's rows.

7. Return an AgentResult with notes like:
   "10 gaps Â· top: kubernetes (31 listings, cost 24.1) Â· 58 listings analysed"

8. Register "gap_analyzer" in the agent registry and add it to the cycle
   after the scorer. One line each.

9. A `python -m edgedash.gaps` command that prints the latest snapshot as a
   readable table: rank, skill, listings blocked, opportunity cost, mean
   score, and a text bar. This is the thing I will actually look at every
   morning, so make it readable in a terminal.

Show me the opportunity_cost computation first. I want to read the
arithmetic before anything else.
```

### Why `opportunity_cost` and not just a count

Say Kubernetes is missing from 2 listings, and Terraform is missing from 2 listings. Raw count
says: tie.

But the Kubernetes listings score **82 and 79** â€” jobs you'd genuinely get an interview for.
The Terraform ones score **31 and 24** â€” wrong seniority, wrong city. Terraform isn't what's
stopping you from getting those; *everything* is.

```
opportunity_cost = sum(listing.score / 100 for each blocked listing)

  kubernetes:  0.82 + 0.79 = 1.61   â† expensive
  terraform:   0.31 + 0.24 = 0.55   â† nearly free
```

Same raw count of 2. Three times the weight. **A raw count tells you what the market mentions.
A weighted count tells you what's blocking you.**

`also_nice_to_have` is tracked separately and never merged in, because "required in 30 listings"
and "preferred in 30 listings" are completely different facts. Merge them and you'll go learn
something that was never blocking you.

**Then wire it in and run:**

```bash
python run_cycle.py
python -m edgedash.gaps
```

**This is the moment of the class.** Read your own table. Then **drill into your top gap** using
its `example_ids` and look at the actual job listings it came from. Rule 26 exists precisely so
that when the number surprises you, you can check it rather than argue with it.

## PROMPT C4-P5 â€” The alias helper, on a leash

**What it does:** The only model call in today's work. It **suggests** aliases and changes
nothing.

```text
Add an alias suggestion helper. This is the ONLY model call in today's

1. Collect the canonical skill strings that appear in the database and are
   NOT already in the alias map, with their counts.

   that refer to the same underlying skill. Schema: a list of
   {canonical: str, variants: list[str], confidence: "high"|"low"}.
3. Print the proposals as READY-TO-PASTE config.yaml alias-map YAML.
   Write NOTHING to config.yaml. Do not modify any file.
4. Print a warning above the output stating these are suggestions that
   need my review, and that merging distinct skills is worse than leaving
   them separate.
5. Any proposal grouping strings I already have as separate entries in my
   alias map must be flagged loudly as a conflict with my existing choice.

```

**Expect it to over-merge something.** When it does, that's the demonstration â€” you disagree,
and nothing happened, because it printed YAML instead of editing your config.

**The pattern worth stealing for your own work:** *model in the loop, not in the pipeline.* It
does the tedious part â€” reading 300 strings and spotting patterns, which it's genuinely good at
â€” and the decision stays with the person who lives with the consequences. The difference between
"the model suggests, I approve" and "the model decides" is about four lines of code, and it's the
difference between a tool you can trust and one you can only hope about.
