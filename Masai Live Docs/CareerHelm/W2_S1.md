## The one idea this class is built on

Before the prompts, the reframe everything below depends on:

> **Don't ask the model to score. Ask it to read, and do the arithmetic yourself.**

Asking an LLM for "a fit score out of 100" gives you a number that is:

- **inflated** â€” models are agreeable, so nearly everything lands in the 80s
- **non-deterministic** â€” same listing twice, two different numbers, and neither is "true"
- **unexplainable** â€” the only available answer to "why 88?" is "because it said so"
- **untestable** â€” you cannot write a unit test against a vibe

So we split the work in two:

| The model does | Your code does |
|---|---|
| Reads the job description | Compares facts to your profile |
| Returns **facts**: required skills, seniority, years, remote | Computes four weighted components |
| Never sees your weights | Produces the score and the reason string |
| Fuzzy, costs money, cached | Deterministic, free, unit-tested |

Everything below is the implementation of that one table.

## PROMPT C3-P2 â€” One door to the model

**What it does:** The single module that knows an AI provider exists. Same pattern as
`get_json` last week â€” one door to the outside world, so the retry and the rate limit get
written once instead of remembered every time.

```text
Create edgedash/llm.py â€” the single door to any language model, per
steering rule 15.

1. One public function:
   complete_json(prompt: str, schema: dict, *, max_retries: int = 1) -> dict

   - Sends the prompt, requests JSON output, parses it, and validates the
     result against `schema` before returning.
   - If parsing or validation fails: retry ONCE with an appended
     instruction stating the exact validation error and that the reply
     must be JSON only, no prose and no markdown fence.
   - If it fails again, raise a clear custom LLMError. Callers handle it
     per rule 17 â€” this function must not swallow failures silently.
   - Strip markdown code fences and any leading/trailing prose before
     parsing. Models add these constantly; handle it, don't hope.
   - Rate limit internally per rule 15: minimum 1 second between calls,
     and a rolling cap of 15 calls per minute. Sleep, don't error.
   - On a 429 or quota error, exponential backoff, 3 attempts, then raise.

2. Provider behind config, never hardcoded:
   - Read `llm_provider` and `llm_model` from Config.
   - Support "gemini" (google-generativeai, key from GEMINI_API_KEY) and
     "ollama" (local HTTP, no key, for anyone who won't sign up).
   - Selecting a provider must be a config change only. Adding a third
     provider must not require editing complete_json.
   - Missing API key: raise a clear, actionable error naming the env var
     and the .env file â€” do not fall back silently to another provider.

3. Add GEMINI_API_KEY= to .env.example. Confirm .env is still gitignored.

4. Add a tiny CLI check: `python -m edgedash.llm --check` sends one
   trivial prompt and prints the provider, model, and whether it worked.

Show me llm.py, then the exact command to run the check.
```

**Then run the check:**

```bash
python -m edgedash.llm --check
```

**Check before moving on:** the check passes and prints your provider and model. If it fails
here, fix it now â€” every prompt below this one depends on it, and debugging a key problem is
much easier when it's the only moving part.

**The detail worth noticing:** the retry doesn't just try again, it retries *telling the model
what was wrong*. "You returned this, it failed because this field was missing, JSON only." That
one detail is the difference between an unreliable pipeline and a reliable one, and almost
nobody does it.

## PROMPT C3-P3 â€” The Extractor

**What it does:** The only part of your project that calls a model. It reads a job description
and returns facts. It does not score anything, and it does not know you exist.

```text
Build the extraction step â€” the only part of the Scorer that calls a model.

edgedash/agents/extractor.py

1. A schema for what we extract from a job description. EXACTLY these
   fields, nothing else:
     required_skills: list[str]   â€” skills the role requires
     nice_to_have:    list[str]   â€” preferred, not required
     seniority:       one of "junior" | "mid" | "senior" | "lead" | "unknown"
     years_required:  int | null  â€” null if not stated, never a guess
     remote_ok:       bool | null â€” null if the listing doesn't say

   Rule 16: there is no score field here and there must never be one.

2. `extract(listing: dict) -> dict` which:
   - Computes a stable hash of the job description text.
   - Checks the extraction cache FIRST. On a hit, return it and make no
     model call at all.
   - On a miss, calls llm.complete_json with the schema, stores the result
     in the cache keyed on that hash, and returns it.
   - Normalises skill names to lowercase before storing, so "Postgres"
     and "postgres" match later.

3. The prompt inside extract() must:
   - Ask ONLY for what the listing says. Explicitly instruct: do not infer,
     do not guess, do not evaluate the candidate. If the listing doesn't
     state something, the field is null or an empty list.
   - Not mention my profile, my skills, or scoring at all. The model must
     not know a candidate exists â€” it is reading a document, nothing more.

4. Cache storage goes through the existing storage module per rule 2 â€” no
   direct sqlite3. Add whatever table or column it needs there, with a
   migration that is safe to run on an existing database.

Show me the schema and the prompt text first, then the rest.
```

**Then test it on one listing.** Kiro will give you a one-liner for your codebase; it'll look
something like:

```bash
python -c "from edgedash.agents.extractor import extract; from edgedash.storage import get_listings; import json; print(json.dumps(extract(get_listings(limit=1)[0]), indent=2))"
```

**Run it twice.** The second run should be instant â€” that's the cache. No API call, no quota
used.

**Check before moving on:** open the actual job description next to the output. Did it get the
skills right? Is `years_required` null on a listing that genuinely doesn't state years?

**Why the prompt doesn't mention you:** a model that knows whose profile it's comparing against
starts being *helpful* â€” softening a requirement you don't meet, emphasising an overlap. Not
maliciously; it's trained to be encouraging, and to a model "useful" and "encouraging" are hard
to separate. So it never finds out a candidate exists. It reads a document. The comparison
happens later, in code that has no feelings about the outcome.

## PROMPT C3-P5 â€” Re-score on demand (optional but genuinely useful)

**What it does:** Rule 18 means listings never get re-scored â€” which is correct for cost, and
annoying the moment you want to tune a weight. This gives you an explicit, deliberate way to
invalidate scores.

```text
Add a re-scoring escape hatch: `python -m edgedash.rescore`.

Rule 18 says never re-score automatically, and that stays true. This is a
manual command I run on purpose.

- `--all` clears every score so the next cycle re-scores everything.
- `--id <listing_id>` clears one listing's score.
- Clears score, reason, components and scored_at â€” but NEVER the
  extraction cache, so re-scoring costs zero API calls. This is the whole
  point of the command.
- Print how many scores were cleared and remind me to run the cycle.
- Refuse to run --all without a confirmation prompt.

Read/write through the storage module only, per rule 2.
```

**Why this is worth ten minutes:** the loop `edit weights â†’ rescore --all â†’ run cycle â†’ look at
ranking` is how you actually tune your scorer, and because extraction stays cached it's free
and fast. Without this you'd either re-pay for extraction or hand-edit the database.
